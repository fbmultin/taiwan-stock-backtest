## 1. 背景與目標

### 1.1 起因
- 使用者（Adam）看到台灣財經作者清流君、股魚的「逢低加碼」文章，想自己驗證。
- 清流君：196 種「逢低買進」參數組合，回測 0050（2003/6/30 上市起），結論是多數組合輸給直接買進持有，等待有成本。
- 股魚：主張 0050 回檔約 5%–7% 加碼效率最佳、從高點回落約 10% 停利；其統計基準不明確、樣本短、聲明排除極端值。
- 兩者的底層機制相同：用固定百分比判斷相對高低點，差別只在觸發後的動作與初始持倉。

### 1.2 使用者實際需要的是「提醒」，不只是回測
- 輸入任一檔 ETF → 顯示該檔的回檔門檻與統計結果。
- 「我的持股」依當天股價標示加碼區或停利區。
- **不做推播通知**，使用者打開 app 才看到。
- 做成**獨立分頁**，不改動既有頁面，共用既有資料層。

### 1.3 設計原則
- 門檻與參數必須有**學術依據或由資料算出**，不接受憑空寫死的數字。
- 誠實顯示結果：「無優勢」「證據不足」「資料不足以判斷」都是正當的輸出，不為了讓畫面好看而硬給門檻。

## 2. 決策與理由

### 2.1 比較基準：選 B′，不選 A 或 B

要檢定的問題必須先定義，因為它決定檢定用的績效差序列 `d` 怎麼構造。

| 方案 | 問法 | 構造 | 主要問題 |
|---|---|---|---|
| **A** | 跌到某深度後買，後續報酬比「平常任一天買」高嗎？ | 訊號日的未來 h 日報酬，減去平均 | 相鄰訊號日的未來報酬**高度重疊**，有效樣本只剩約 n/h，檢定力很低；需要很長的區塊長度，結果對區塊長度敏感 |
| **B** | 整套「等訊號才買」的策略，整體贏過買進持有嗎？ | 規則日報酬減買進持有日報酬 | 規則大部分時間持有現金，必然少賺；結果被**現金拖累**主導，幾乎必定輸，無法判斷訊號本身有沒有資訊（這是清流君的問法） |
| **B′（採用）** | 扣掉「單純少持股」的影響後，訊號是否讓你在漲的日子多持股、跌的日子少持股？ | 規則日報酬減「平均曝險相同的固定比例組合」日報酬 | 見 2.1.1 |

#### 2.1.1 B′ 的性質與限制
- 逐日序列，**不用重疊的未來報酬**，統計上比 A 乾淨。
- 對照基準與規則的平均曝險相同，所以不會因為「曝險低」就必輸，比 B 公平。
- 代數上 `d̄_k` 等於「持股部位 `pos` 與超額報酬 `r−c` 的樣本共變異數」（見 3.4）。因此 B′ 檢定的是**擇時資訊**，**不等於**「現在加碼的期望報酬是多少」。
- 畫面上另放描述性數字（例如「歷史上跌到 −10% 後 12 個月的中位數報酬」），**明確標示為描述性、未經顯著性檢定**。
- 同一張 `d` 的輸出可以另外算 B（對買進持有）當對照，供使用者看到兩個答案。

### 2.2 檢定方法：SPA 與 StepM，取代手調的經驗值

原本草案用 70/30 切分、事件數 ≥ 8、「後段保留前段一半優勢」等經驗值。查證後決定改用多重比較檢定：

- 原因一：Bailey 等人（2015/2017）指出，hold-out 這類標準防過擬合手法在投資回測上往往不可靠，所以 **70/30 切分降為輔助檢查，不當主要防線**。
- 原因二：White 的 Reality Check 這一族用**全部歷史**做檢定，不需要切出一段不能碰的資料。ETF 歷史本來就不長，這點很重要。
- 原因三：事件數少時，檢定的標準誤自然變大、過不了關，不需要人為訂「≥ 8」。
- Harvey、Liu、Zhu（2016）主張多重檢定下顯著性門檻應比一般的 t > 2 嚴格（建議 t > 3.0）。他們的研究對象是橫斷面報酬因子，**不能直接套用數字**，只用來支持「顯著水準不要用最寬鬆的 5% 以上」的方向。

### 2.3 實作位置：瀏覽器內的 JavaScript，不走 Python 預先計算

**決定**：路線 (a) 用 JavaScript 重寫，在前端算。**【不採用】**路線 (b)（Python 預先算好存資料庫）。

理由（使用者提供，已確認）：
- app 是純前端 SPA，沒有自己的後端 server。
- 股價歷史資料的抓取，前端已有可行且免登入的管道：`dataCache.js` 依序嘗試 FinMind → TWSE → Yahoo，失敗就換下一個。
- Firestore 共用快取是「加分項、非必要」：只有登入 Google 帳號時才讀寫（程式碼有 `if (!currentUid) return null`），且單筆文件有 1 MiB 上限，20 年以上的日資料不保證存得下。它不是給外部程式批量讀取用的。
- 路線 (b) 一樣得把股價歷史餵給外部 Python 環境，會卡在資料存取；還要多維護 GitHub Actions 排程，對沒有程式背景的使用者是長期負擔。
- 路線 (a) 讓檢定變成 app 裡的一個功能（按鈕觸發，和「更新排名表」「開始回測」同一種體驗），直接沿用瀏覽器已抓到的資料。

### 2.4 其他決策
- **回看窗口固定為 60 與 252 個交易日**，是「定義」不是掃描參數。依據只是市場慣例（約一季、52 週），**沒有證據顯示它們最佳**。必須另做穩健性檢查（見 8.4）。
- **「高原區」（最佳門檻的相鄰門檻也都不錯）【不採用】為判定標準**：它是啟發式做法，沒有查到學術依據。只可作畫面輔助。
- **提醒只在 app 內顯示**，不做推播。
- **持股提醒只放新分頁**（第一版不動 `PortfolioTracker.js`），穩定後再決定要不要在持股頁加徽章。

## 3. 資料與規則定義

### 3.1 輸入資料
- 該檔 ETF 的**還原日股價（含息）**，從上市日到最新交易日；來源為既有 `dataCache.js`。
- 0050 約 2003/6/30 起，約 5,000–5,600 個交易日。
- 日報酬 `r_t = P_t / P_{t-1} − 1`（還原價）。
- 現金日利率 `c_t`（見 3.6）。
- **【待驗證】分割與還原**：`src/data/twStockSplits.js` 負責處理分割。動工時必須檢查含分割的歷史不會出現假性崩跌（例如單日報酬異常負值）；若價格序列異常，狀態應為「資料不足以判斷」。

### 3.2 訊號（回檔）
對回看窗口 `N ∈ {60, 252}`（交易日）：

```
H_t  = max(P_{t-N+1}, ..., P_t)          // 含當日的滾動高點
DD_t = P_t / H_t − 1                      // 回檔幅度（≤ 0）
```

- 規則 k 的訊號：在第 `s` 天**收盤後**，`DD_s ≤ −x_k` 且前一天 `DD_{s-1} > −x_k`（首次跌破）。
- 前 `N−1` 天沒有完整窗口，不產生訊號。

### 3.3 持股部位 `pos(k,t)`
- 訊號在第 `s` 天收盤後確認，假設以當天收盤價進場，所以曝險從第 `s+1` 天的報酬開始，持有 `h_k` 個交易日：

```
pos(k,t) = 1  若存在訊號日 s，使得 s+1 ≤ t ≤ s+h_k
pos(k,t) = 0  其餘
```

- 多個訊號的持有區間重疊時，部位仍是 1（取聯集），**不需要為了 `pos` 去重**。
- 這個「收盤後確認、隔天起算報酬」的時序是為了避免偷看未來（look-ahead），改動時必須保留。
- 「事件」的去重規則（只用於畫面上的事件數、勝率等描述性數字）**【待決定】**：暫定提案為「同一波下跌只算一次，回檔回到 −x/2 以內才重新計算」。

### 3.4 績效差 `d(k,t)`（B′ 的核心）

```
x_t     = r_t − c_t                          // ETF 相對現金的超額報酬
f_k     = (1/n) · Σ_t pos(k,t)               // 規則 k 的平均曝險
d(k,t)  = ( pos(k,t) − f_k ) · x_t
```

推導：規則 k 的日報酬是 `pos·r + (1−pos)·c`；對照基準是「永遠持有 `f_k` 比例的 ETF、其餘放現金」，日報酬是 `f_k·r + (1−f_k)·c`。兩者相減：

```
[pos·r + (1−pos)·c] − [f_k·r + (1−f_k)·c] = (pos − f_k)(r − c)
```

性質：`d̄_k = (1/n) Σ (pos−f_k)·x_t` 等於 `pos` 與 `x` 的樣本共變異數。正值代表「規則持股的日子，超額報酬平均較高」。

- 符號約定：`d` **正值代表規則較好**（原型與本文件一致；Python `arch` 用的是「損失差 = 基準 − 模型」，方向相反，對照時要處理，見第六章第 2 點）。
- 檢定的虛無假設：`H0: max_k E[d_k] ≤ 0`（沒有任何一條規則的擇時資訊優於基準）。

### 3.5 規則集合 K 【待決定】
暫定提案：

- 回檔門檻 `x ∈ {3%, 4%, …, 20%}`（18 檔，1% 一格）
- 持有期 `h ∈ {63, 126, 252}` 個交易日（約 3、6、12 個月）
- 回看窗口 `N ∈ {60, 252}`
- 共 18 × 3 × 2 = **108 條規則**

另一個傾向（待定）：格子對所有 ETF **固定**，不隨歷史長度調整；歷史短的 ETF 讓進場次數不足的規則被剔除（見第九章）。固定格子的好處是不同 ETF 的結果可以並排比較。

### 3.6 現金日利率 `c_t` 【待決定】
暫定做成進階設定，預設值待定（例如固定年化利率換算日利率）。**必須檢查結論對它是否敏感**（見 8.4）。

## 4. 統計檢定公式

符號：`n` = 交易日數，`K` = 規則數，`B` = 重抽樣次數，`L` = 平均區塊長度。

### 4.1 平穩自助法（Politis & Romano, 1994）
重抽樣出長度為 n 的索引序列 `τ(1..n)`：

- 區塊起點在 `{0..n−1}` 均勻抽取；
- 區塊長度為幾何分配：`P(len=j) = p(1−p)^(j−1)`，`p = 1/L`，平均 L；程式用 `len = 1 + floor( ln(1−U) / ln(1−p) )`；
- 區塊**環狀接尾**（超過 n 就繞回 0）；
- 湊滿 n 個為止，最後一個區塊截短。

重抽樣後的平均：`d̄*_{k,b} = (1/n) Σ_t d(k, τ_b(t))`。

**關鍵：同一次重抽樣 b 的索引對所有規則 k 共用。**

### 4.2 SPA（Hansen, 2005）

```
d̄_k   = (1/n) Σ_t d(k,t)
ω̂²_k  = (n/B) Σ_b ( d̄*_{k,b} − d̄_k )²           // 用重抽樣本身估變異數（正式版）
t_k    = √n · d̄_k / ω̂_k
T_SPA  = max( max_k t_k , 0 )
A_n    = √( 2 · ln ln n )
```

三種重新置中（recentering）版本：

| 版本 | `μ_k` | 意義 |
|---|---|---|
| upper | `d̄_k` | 等同 White 的 Reality Check，最保守（p 值最大） |
| lower | `max(d̄_k, 0)` | 表現差的規則不重新置中，最寬鬆（p 值最小） |
| consistent | `d̄_k`（若 `t_k ≥ −A_n`），否則 `0` | 把「明顯很差」的規則排除在外，介於兩者之間 |

```
T*_b(v) = max( max_k √n · ( d̄*_{k,b} − μ^v_k ) / ω̂_k , 0 )
p_v     = (1/B) · #{ b : T*_b(v) > T_SPA }           // 嚴格大於
```

設計決定：**以 consistent 為主要 p 值**，同時顯示 lower 與 upper 當範圍；三者結論一致才算穩固。【待決定：是否採此顯示方式，見第八章】

說明：consistent 的門檻 `√(2 ln ln n)` 是依 `arch` 套件的實作（見 5.4）寫成的，**尚未對照 Hansen 原文逐式確認**。

### 4.3 StepM（Romano & Wolf, 2005）
重用同一批重抽樣：

```
Z*_{b,k} = √n · ( d̄*_{b,k} − d̄_k ) / ω̂_k
S = {1..K};  R_total = ∅
重複：
    c  = Z* 在集合 S 上逐次取最大值後，第 (1−α) 分位數
    R  = { k ∈ S : t_k > c }
    若 R 為空 → 停止
    R_total ∪= R;  S = S \ R
輸出 R_total（被判定為「優於基準」的規則集合）
```

- 分位數實作：升冪排序後取索引 `ceil((1−α)·B) − 1`。
- 目的：控制整體錯誤率（FWER），並告訴我們**哪些**規則各自顯著，而不只是一個總 p 值。
- 近似：本實作的 `ω̂` 是全樣本、各步共用，**不是** Romano–Wolf 原文那種巢狀（nested）重抽樣；見第六章第 8 點。

### 4.4 累積和加速
令 `C[t,k] = Σ_{i<t} d(i,k)`（`C[0,k]=0`）。一個區塊 `[s, s+len)` 的加總：

- 不繞回：`C[s+len,k] − C[s,k]`
- 繞回：`C[n,k] − C[s,k] + C[s+len−n,k]`

每個區塊只需 O(K) 次運算。一次重抽樣的成本從 O(n·K) 降為 O((n/L)·K)。需要的記憶體約為 `(n+1)·K·8` 位元組（n=5200、K=108 約 4.5 MB）加上 `B·K·8`（B=1000 約 0.9 MB）。

## 5. 已驗證的實作細節

### 5.1 驗證方法
- 參考原型：Node.js 22（`spa_stepm_prototype.js`，完整程式碼見附錄 A）。
- 對照對象：Python `arch` 8.0.0 的 `SPA` 與 `StepM`。
- 測試資料：**人工合成**，非真實行情。AR(1) 共同因子（係數 0.3）加上獨立雜訊，n=1200、K=20，三組不同種子（7、11、21），規則平均績效差分成「明顯為負」「零」「小幅為正」三類。
- 對照時 JS 端使用**解析變異數**（`analyticOmega2`，平穩自助法平均數的精確變異數），與 `arch` 的變異數公式一致；正式版改用重抽樣變異數（見 5.3）。

### 5.2 結果【已驗證】

| 檢查項目 | 結果 |
|---|---|
| 累積和版 vs 逐日加總版（相同亂數序列）的重抽樣平均 | 最大絕對差 ≈ 1e-15（三組資料皆是） |
| 變異數：JS 解析版 vs `arch` | 最大相對差 ≈ 6e-14 |
| 資料集 3（邊緣顯著，T≈2.68）SPA p 值：JS（B=20000）lower / consistent / upper | 0.02595 / 0.0312 / 0.0381 |
| 同資料集，`arch`（預先標準化，reps=20000） | 0.0244 / 0.0306 / 0.0379（差異在蒙地卡羅誤差內） |
| 資料集 3 StepM 選出集合 | JS 與 `arch` 皆為 `[18]` |

### 5.3 重抽樣變異數 vs 解析變異數【已驗證】
資料集 3：正式版（重抽樣變異數）T = 2.665、p = 0.02585 / 0.03115 / 0.03815；解析版 T = 2.680、p = 0.02595 / 0.0312 / 0.0381。差異極小。正式版採重抽樣變異數是因為成本幾乎為零，而解析版是 O(n²)，n=5000 時太慢。

### 5.4 `arch` 8.0.0 的 `studentize` 參數沒有作用【已驗證，僅限此版本】
- 讀 `arch.bootstrap.multiple_comparison` 原始碼：`studentize` 只被用在 `_info` 字串；`compute()` 比較的是 `max(平均績效差)` 與重抽樣的 `max(平均 − 置中值)`，**沒有除以標準差**。變異數僅用於 consistent 版本的「是否排除」門檻。
- 實測：`SPA(..., studentize=True)` 與 `studentize=False`，同種子下 p 值完全相同。
- 因此 **`arch` 的 `SPA`/`StepM` 實際是未標準化版本**。要得到 Hansen 的 studentized 版本，必須**自行先把每欄除以其標準差**再餵進去（做法見附錄 B）。
- 只確認 8.0.0；其他版本沒查。
- 對照時 `arch` 的 `max` 沒有與 0 取大值，Hansen 原式有；只有在「所有規則的 `d̄` 都為負」時才會造成 p 值些微差異（資料集 1 即是）。

### 5.5 驗證的範圍限制
- 僅用合成資料、n=1200、K=20、`L=20`。**n≈5200、K=108 與真實行情**尚未對照 `arch` 驗證（只做過效能測試，見第七章）。
- 驗證對象是 SPA/StepM 引擎本身，**不包含** `d` 的構造（3.2–3.4）。`d` 的構造需在第十章 Step 4 用真實資料另行對照。

## 6. 十個容易翻錯的地方

每點都列「做法」「為什麼」「翻錯會怎樣」。

**1. 所有規則共用同一組重抽樣索引。**
為什麼：規則之間高度相關（例如 −10% 與 −12% 的訊號幾乎同時發生）。共用索引才能保留這個相關結構，讓「最大統計量」的分布正確。
翻錯：每欄各抽各的，等於假設 K 條規則彼此獨立；正相關的情況下，獨立副本的最大值會偏大，臨界值被高估，結果通常**過度保守**（該判有效卻判不出來）。方向取決於相關結構，但無論方向，p 值都失準。

**2. 正負號：本文件用「績效差，正為好」。**
為什麼：檢定的備擇假設是「某規則優於基準」，統計量取最大值。
翻錯：與 `arch`（損失差 = 基準 − 模型，正為基準較好）混用，整個檢定反向，所有結論顛倒。對照 `arch` 時，要餵 `-d`。

**3. 用 `Float64Array`，不要用 `Float32Array`。**
為什麼：累積和相減是「兩個大數相減」，捨入誤差會被放大。
翻錯：32 位元的有效位數約 7 位，區塊加總會出現可見誤差，p 值有系統性偏差，且不易察覺。

**4. 用自己寫的、可設種子的亂數產生器（原型用 mulberry32）。**
為什麼：`Math.random` 不能固定種子。
翻錯：同一份資料每次按按鈕 p 值都不同，使用者無法分辨是資料變了還是運氣；快取內容也無法重現。

**5. 種子要「每次重抽樣各一個」（例如 `seed_b = hash(baseSeed, b)`）。【未實作】**
為什麼：Worker 要把重抽樣分批、甚至平行執行。每次重抽樣有自己的種子，結果才與「怎麼分批、先後順序」無關。
翻錯：**目前原型只用一條亂數序列**（先抽 B 次再算）。如果直接把它改成分批，結果會依批次切法而變，同一份資料不同分批方式得到不同 p 值。這一點正式版必須補上。

**6. `T` 要與 0 取最大值；p 值用嚴格大於；注意解析度只有 1/B。**
為什麼：這是 Hansen 的定義；嚴格大於避免 B 次中恰好相等時偏向顯著。
翻錯：忘了與 0 取最大，所有 `d̄` 為負時 p 值會算錯。p 值解析度：B=1000 時，p 約 0.05 的標準誤約 ±0.007，正式判定的 B 建議 ≥ 5000；p=0 應顯示成「< 1/B」，不要顯示成 0。

**7. 區塊長度 L 必須做敏感度檢查（尤其在 `d` 有序列相關時）。【待驗證】**
為什麼：區塊太短，重抽樣會打散真實的序列相關，低估變異，p 值偏小，造成**假陽性**。A 法的 `d` 因為未來報酬重疊，L 理論上必須接近持有期 h（數百天），這就是不用 A 的原因之一。B′ 的 `d` 是逐日序列，**推論**序列相關很弱、L 不必很長，但這個推論**尚未用模擬驗證**，見 8.1 與 Step 0。

**8. StepM 的變異數是近似。【近似，僅與 `arch` 對照過】**
為什麼：Romano–Wolf 原文每一步用巢狀重抽樣估計標準誤；本實作用全樣本的 `ω̂`、各步共用，省下大量運算。
翻錯：標準化是近似，檢定水準可能略偏。只確認過「與 `arch`（同樣是近似做法）結果一致」，**沒有驗證它與巢狀版本的差異**。

**9. 區塊長度 L 目前手動指定，Politis–White 自動選擇法【未實作】。**
為什麼：Politis 與 White（2004）提出自動估計最佳區塊長度的方法，後由 Patton、Politis、White（2009）修正公式；需要用修正版。
翻錯：L 太短 → 假陽性（同第 7 點）；L 太長 → 檢定力下降。在實作自動選擇之前，**必須同時報告 L ∈ {10, 20, 60, 250} 的結果**，結論若隨 L 劇烈變動，視為不穩定。

**補充（2026-10-04）**：Python 端可用 `arch.bootstrap.optimal_block_length` 對 `d` 算出區塊長度的**參考值**（回傳欄位名稱與適用的自助法類型動工時再確認），作為 L 敏感度檢查（8.4）的對照。這只是參考值，**不能取代**在 JavaScript 端實作 Politis–White 自動選擇法；在實作完成之前，第 9 點的「同時報告多個 L」仍然有效。

**10. 沒有任何規則可檢定（K=0）時，不可回傳 p=0，也不可算成拒絕。**（2026-10-05 Step 0 重跑發現）
為什麼：所有規則的進場次數都低於下限時，規則全被剔除，沒有東西可檢定。原型在空集合上取最大值得到 0，p 值就變成 0。
翻錯：這條路徑會被誤算成「判有效」，假陽性率被高估（案例 A 的 L=5 從 6.28% 變成 6.35%）。正確做法：K=0 時狀態為「資料不足以判斷」；模擬彙整時不算拒絕，但仍算在分母。

3. 某規則的進場次數（去重後）< 5 → 該規則剔除出 K，不參與檢定。
4. 剔除後 `K = 0` → 資料不足。
5. 價格序列異常（缺漏、疑似未還原的分割跳空）→ 資料不足，並提示原因。

#### 10.1.1 執行細節與判讀方式的事前登記（2026-10-04，跑出任何結果之前寫入）
上面的通過標準沒有寫明「看哪個統計量」「兩種虛無是否都要過」，動工時補上如下，**之後不得依結果回頭改**：

### 14.2 C 級項目的補強規格

#### 14.2.1 停利回落%
- **第一版**：停利是「使用者自訂的提醒」，**不經過檢定**。預設 10% 沿用股魚的公開範例。畫面必須標示「自訂設定，未經檢定；預設值來自股魚公開範例」，**不得出現任何「此停利點有效或較佳」的文字**。
- **【待設計】出場規則的檢定**：理論上可以沿用 B′ 的 `d` 形式（部位由出場規則決定），但出場規則**必須同時定義再進場規則**，否則部位會永遠停在 0。這會增加參數，列入第二期，不屬於第一版。
- **對範圍的影響**：使用者的原始想法是「高點停利、低點買回」。第一版只有「加碼」這半邊會被檢定，停利半邊沒有。這點要寫進對使用者的說明。

#### 14.2.2 任意數字的敏感度檢查
這幾個數字沒有理論可依，不嘗試找理論，改成**確認結論是否依賴它們**。一次只改一個參數，其餘維持基準值。

| 參數 | 變體（基準加粗） | 影響範圍 |
|---|---|---|
| 去重回復閾值 | 回到 −x/4；**回到 −x/2**；回到近期高點 | 僅第一層的事件數與描述數字 |
| 進場次數下限 | 3；**5**；8 | 影響哪些規則進入 K，需重跑檢定 |
| 資料長度規則的除數 | 15；**20**；30 | 影響各檔可用的持有期與整檔是否可檢定，需重跑檢定 |
| 近期窗口 | 3；**5**；7 年 | 僅近期一致性的描述 |

- **穩健判定**【暫定】：四種狀態（第九章）與第一層的方向，在**全部變體**下都相同，才算穩健；否則畫面加警示「此結論對設定敏感」，並列出是哪個參數造成差異。
- **限制**：這只能說明「結論不依賴這個任意數字」，**不能證明數字本身正確**。
- **運算成本**：需要重跑檢定的變體約 4 個；依第七章實測（K=100、B=1000 約 0.13 秒），規則集合縮小後更快，成本可忽略。

#### 14.2.3 顯著水準與 p 值顯示
- StepM 以 α=0.05 判定「有效」，另外**同時顯示 α=0.01 下是否也成立**（標示為「較強證據」）。「證據不足」維持 SPA consistent p ≤ 0.10，畫面標示為慣例。
- p 值一律連同**蒙地卡羅標準誤** `√(p(1−p)/B)` 顯示；p=0 顯示為「< 1/B」。
- 狀態判定使用 B ≥ 5000；探索性畫面可用 1000，但必須標示。
- 若日後顯示 t 統計量，需說明多重檢定下的門檻比一般的 2 更高（Harvey 等人）。

#### 14.2.4 第一層描述性數字的不確定性
- **事件群**：依時間排序，第一個事件開啟第一群；之後第一個進場日 ≥ 該群起始日 + h（持有期）的事件，才開啟下一群。`N_eff` ＝ 群數，稱為「不重疊事件群數」，作為有效樣本數的粗略估計。統計只取各群「第一個事件」的後續報酬。**注意**：這只保證各群的後續報酬期間不重疊，不保證是獨立的市場事件（連續兩群可能處於同一段空頭）。（2026-10-05 修訂：原文為「持有期窗口互相重疊的進場日併為一群」的串連寫法，改採此定義；原因是串連法會在長空頭中把一長串事件併成一群，浪費資訊。）
- 對每個「門檻 × 持有期」顯示：事件數、`N_eff`、後續報酬的中位數與勝率，**以及「平常任一天買」同期的中位數與勝率當對照**，另顯示與對照的差（中位數差與勝率差，單位為百分點）。對照範圍是從第 N 天起、之後仍有完整 h 天報酬的每一天。
- 區間：以**事件群為單位**做自助法，給 90% 區間。**【待驗證】** 區間的實際涵蓋率要用模擬檢查：在 GARCH 虛無路徑上，名目 90% 的區間實際包含真值的比例是否接近 90%。
- `N_eff` < 5 時，**不顯示中位數、勝率與區間**，只顯示事件數、`N_eff` 與「樣本太少」。
- 全部標示「描述性，未經顯著性檢定」。
- **（2026-10-05）Step 0 重跑結果**：在 GARCH 路徑上，名目 90% 的區間實際涵蓋率約 85%–87%（案例 A 為 85.4%），偏窄；N_eff 中位數約 9 至 11。第一層上線前必須校正，或明確標示為近似（見 10.1.3、13.10）。

#### 14.2.5 跨 ETF 多重檢定
- 每次查詢獨立檢定。同時查很多檔時，即使全部都沒有優勢，偶然出現「有效」的機會會上升（若彼此獨立，查 20 檔在 5% 水準下預期約 1 檔）。
- **第一版**：畫面提示，不做校正。
- **若日後做「全部 ETF 排行」或批次掃描**：必須先處理多檔校正（FDR 控制，例如 Benjamini–Hochberg 等，**【待查證】**），未處理前不得上線。

原型，已與 `arch` 對照驗證（第五章）。**尚未實作逐次重抽樣種子**（第六章第 5 點）、Politis–White 區塊長度（第 9 點）。正式版需補上並改寫成專案的 ES module 與繁中註解風格。**原型在沒有任何規則可檢定（K=0）時會回傳 p=0，使用前必須先處理（見第六章第 10 點）。**

```js
'use strict';
// 可種子化的亂數產生器(Math.random 無法固定種子,同一份資料會得到不同 p 值)
function mulberry32(a){return function(){a|=0;a=a+0x6D2B79F5|0;let t=Math.imul(a^a>>>15,1|a);t=t+Math.imul(t^t>>>7,61|t)^t;return((t^t>>>14)>>>0)/4294967296;};}

// d: 列優先 Float64Array,d[t*K+k] = 規則 k 在第 t 天相對基準的績效差(正=規則較好)
function cumsum(d,n,K){const C=new Float64Array((n+1)*K);for(let t=0;t<n;t++){const a=t*K,b=(t+1)*K;for(let k=0;k<K;k++)C[b+k]=C[a+k]+d[a+k];}return C;}

// 平穩自助法:區塊起點均勻、長度服從幾何分配(平均 L),環狀接尾。
// 用累積和讓每個區塊的加總只要 O(K),整體每次重抽樣是 O(n/L*K) 而非 O(n*K)
function bootMeans(C,n,K,B,L,seed){
  const rng=mulberry32(seed),out=new Float64Array(B*K),acc=new Float64Array(K),lq=Math.log(1-1/L);
  for(let b=0;b<B;b++){
    acc.fill(0);let filled=0;
    while(filled<n){
      const s=Math.floor(rng()*n);let len=1+Math.floor(Math.log(1-rng())/lq);
      if(len>n-filled)len=n-filled;
      const e=s+len,sb=s*K;
      if(e<=n){const eb=e*K;for(let k=0;k<K;k++)acc[k]+=C[eb+k]-C[sb+k];}
      else{const nb=n*K,wb=(e-n)*K;for(let k=0;k<K;k++)acc[k]+=C[nb+k]-C[sb+k]+C[wb+k];}
      filled+=len;
    }
    const ob=b*K;for(let k=0;k<K;k++)out[ob+k]=acc[k]/n;
  }
  return out;
}
// 對照用的笨方法(同樣的亂數序列,逐日加總),只用來驗證累積和版本沒寫錯
function bootMeansNaive(d,n,K,B,L,seed){
  const rng=mulberry32(seed),out=new Float64Array(B*K),acc=new Float64Array(K),lq=Math.log(1-1/L);
  for(let b=0;b<B;b++){
    acc.fill(0);let filled=0;
    while(filled<n){
      const s=Math.floor(rng()*n);let len=1+Math.floor(Math.log(1-rng())/lq);
      if(len>n-filled)len=n-filled;
      for(let j=0;j<len;j++){const t=(s+j)%n;for(let k=0;k<K;k++)acc[k]+=d[t*K+k];}
      filled+=len;
    }
    for(let k=0;k<K;k++)out[b*K+k]=acc[k]/n;
  }
  return out;
}
// 平穩自助法平均數的精確變異數(Politis-Romano 權重),僅供和 arch 對照
function analyticOmega2(d,n,K,L){
  const p=1/L,v=new Float64Array(K),m=new Float64Array(K);
  for(let t=0;t<n;t++)for(let k=0;k<K;k++)m[k]+=d[t*K+k]/n;
  const x=new Float64Array(n*K);for(let t=0;t<n;t++)for(let k=0;k<K;k++)x[t*K+k]=d[t*K+k]-m[k];
  for(let t=0;t<n;t++)for(let k=0;k<K;k++)v[k]+=x[t*K+k]*x[t*K+k]/n;
  for(let i=1;i<n;i++){
    const kap=(1-i/n)*Math.pow(1-p,i)+(i/n)*Math.pow(1-p,n-i);
    for(let t=0;t<n-i;t++){const a=t*K,b=(t+i)*K;for(let k=0;k<K;k++)v[k]+=2*kap*x[a+k]*x[b+k]/n;}
  }
  return v;
}
function quantile(arr,q){const s=Float64Array.from(arr).sort();return s[Math.min(s.length-1,Math.max(0,Math.ceil(q*s.length)-1))];}

function spaStepm(d,n,K,o={}){
  const B=o.B??1000,L=o.L??20,seed=o.seed??12345,alpha=o.alpha??0.05;
  const dbar=new Float64Array(K);for(let t=0;t<n;t++)for(let k=0;k<K;k++)dbar[k]+=d[t*K+k]/n;
  const M=bootMeans(cumsum(d,n,K),n,K,B,L,seed);
  let om2=o.omega2;
  if(!om2){om2=new Float64Array(K);for(let b=0;b<B;b++)for(let k=0;k<K;k++){const z=M[b*K+k]-dbar[k];om2[k]+=n*z*z/B;}}
  const sq=Math.sqrt(n),om=om2.map(Math.sqrt),tk=new Float64Array(K);let T=0;
  for(let k=0;k<K;k++){tk[k]=sq*dbar[k]/om[k];if(tk[k]>T)T=tk[k];}
  const A=Math.sqrt(2*Math.log(Math.log(n)));
  const mu={l:new Float64Array(K),c:new Float64Array(K),u:new Float64Array(K)};
  for(let k=0;k<K;k++){mu.u[k]=dbar[k];mu.l[k]=Math.max(dbar[k],0);mu.c[k]=tk[k]>=-A?dbar[k]:0;}
  const pv={};
  for(const v of ['l','c','u']){let cnt=0;
    for(let b=0;b<B;b++){let m=0;for(let k=0;k<K;k++){const z=sq*(M[b*K+k]-mu[v][k])/om[k];if(z>m)m=z;}if(m>T)cnt++;}
    pv[v]=cnt/B;}
  // StepM:每一步只在「尚未被拒絕」的集合上取最大值,重用同一批重抽樣
  const rem=new Set([...Array(K).keys()]),rej=[];
  while(rem.size){
    const mx=new Float64Array(B);
    for(let b=0;b<B;b++){let m=-Infinity;for(const k of rem){const z=sq*(M[b*K+k]-dbar[k])/om[k];if(z>m)m=z;}mx[b]=m;}
    const crit=quantile(mx,1-alpha),nw=[...rem].filter(k=>tk[k]>crit);
    if(!nw.length)break;nw.forEach(k=>{rej.push(k);rem.delete(k);});
  }
  return {T,tk:Array.from(tk),pvalues:pv,stepmRejected:rej.sort((a,b)=>a-b),omega2:Array.from(om2)};
}
module.exports={spaStepm,bootMeans,bootMeansNaive,cumsum,analyticOmega2,mulberry32};
```

## 附錄 B：與 `arch` 對照的 Python 做法

`arch` 8.0.0 不會自動標準化（5.4），必須先自行除以標準差再餵進去。`arch` 的損失差是「基準 − 模型」，所以基準給 0、模型給 `-d`。

```python
import numpy as np
from arch.bootstrap import SPA, StepM

# d: (n, K) 績效差矩陣（正=規則較好）；L: 平均區塊長度
n, K = d.shape

# 1) 取 arch 的解析變異數（私有方法，僅供對照）
s0 = SPA(np.zeros(n), -d, block_size=L, reps=100, seed=0)
s0._compute_variance()
var = s0._loss_diff_var

# 2) 自行標準化，等同 Hansen 的 studentized 版本
ds = d / np.sqrt(var)

# 3) SPA 與 StepM（p 值有三種：lower / consistent / upper）
sp = SPA(np.zeros(n), -ds, block_size=L, reps=20000, seed=5)
sp.compute()
print(sp.pvalues)

sm = StepM(np.zeros(n), -ds, size=0.05, block_size=L, reps=20000, seed=5)
sm.compute()
print(sorted(map(int, sm.superior_models)))
```

注意：
- JS 與 `arch` 使用不同亂數產生器，p 值只能在蒙地卡羅誤差內（B=20000 時約 ±0.003）相符，變異數與統計量則應該近乎完全相同。
- `arch` 的 `max` 沒有與 0 取大值；所有 `d̄_k` 為負時，p 值會有小差異（5.4）。
- 驗證所用的合成資料：AR(1) 共同因子（係數 0.3）＋獨立雜訊，n=1200、K=20、L=20，種子 7、11、21。
